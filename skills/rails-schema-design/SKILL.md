# Rails schema design

Background knowledge consulted while implementing or reviewing migrations, schema changes, and the associations that mirror them.

## 1. References and keys

Model every reference to another table with `t.references ... foreign_key: true`. A bare `bigint` or `integer` id column needs a code comment saying why a foreign key is impossible; without the comment the omission reads as an oversight, and the next migration copies the pattern.

```ruby
# BAD
t.bigint :company_id, null: false

# GOOD
t.references :company, null: false, foreign_key: true
```

Make the foreign key column the same type as the primary key it points to. When the column name differs from the target table, keep `t.references` and name the target.

```ruby
# GOOD
t.references :uploader, null: false, foreign_key: { to_table: :users }
```

Do not drop a foreign key because an import or sync would fail when the parent row is gone. A row pointing at a deleted record is an error the import should surface, and once the constraint is gone every reader of the table has to null-check the reference. Decide how deletion of the parent is handled before the constraint is added, not by removing it.

Declare polymorphic references with `t.belongs_to :x, polymorphic: true` rather than hand-written `x_type` and `x_id` columns, and check `null: false` on the pair. One nullable foreign key per owner type plus a type string is the same pattern in disguise.

```ruby
# BAD
t.integer :user_id
t.integer :partner_id
t.string :integration_type

# GOOD
t.belongs_to :target, polymorphic: true, null: false
```

Link rows to other entities by id, never by a URL or another string copied from the target.

Give every fact exactly one navigation path. Do not attach the same owner to both a parent row and its children, and do not let a record be reachable through two independent chains; the two paths will disagree. When a fact has no row that owns it, find or introduce the concept that does (an answer row owns "this question was asked in this attempt") instead of spreading it over several foreign keys.

Do not add an association that is derivable through associations already present (keyword to middle category to large category). Keep only the direct one.

Record the actor of an event (who sent, who approved) as a required association; missing actor data cannot be reconstructed later.

Preference: mirror the database `on_delete` behaviour in the association (`dependent: :nullify` next to `on_delete: :nullify`) so deletion behaviour is visible in the model.

Preference: express dependent deletion in ActiveRecord rather than `ON DELETE CASCADE`, so callbacks run and the behaviour is visible in the model. When children must not disappear with the parent, use `dependent: :restrict_with_error` or `:restrict_with_exception`.

```ruby
# BAD
t.references :order, foreign_key: { on_delete: :cascade }

# GOOD
t.references :order, foreign_key: true
has_many :line_items, dependent: :destroy
```

## 2. Nullability and booleans

Make boolean columns `NOT NULL` with a default. A nullable boolean is a three-state column, which is what the `Rails/ThreeStateBooleanColumn` cop flags; fix the design rather than excluding `db/schema.rb` from the cop. When the table has no rows yet, add the constraint directly and ignore the add-column-not-null warning.

```ruby
# BAD
add_column :reports, :has_reference, :boolean

# GOOD
add_column :reports, :has_reference, :boolean, null: false, default: false
```

Default every reference to `NOT NULL`. A `null: true` foreign key needs a stated reason in the PR that names the real scenario in which the value is absent.

Make a column nullable when its value is produced asynchronously after the row is created, for example a file generated by a background job in response to the request the row represents.

When a field is optional in the source specification, make the column nullable. Do not normalise `nil` to `''` in application code to satisfy `NOT NULL`; the schema then hides the real optionality.

Use a boolean for a two-state setting. Reach for an enum only when more than two values are concretely expected; `disabled`/`enabled` as a string is a boolean in disguise.

```ruby
# BAD
t.string :auto_reply_setting  # disabled / enabled

# GOOD
t.boolean :auto_reply_enabled, null: false, default: false
```

Preference: "not selected" is an enum value, not `NULL` on a boolean. Check how the schema represents unselected elsewhere and follow it.

## 3. Columns and types

Do not store a value that can be derived from other rows (`previous_status`, `is_current`, a batch-level status, a summary count) without a measured performance need. Derived columns drift from the truth; ordering by the event timestamp already gives the sequence, and item rows already give the batch state. The same applies to attributes computable from a stored file such as filename or content type.

`created_at` and `updated_at` carry no business meaning. Add the event's own timestamp (`status_set_at`, `requested_at`, `attached_at`, `last_actioned_at`) and query, index, and expose that. Insertion time diverges from event time whenever rows are bulk-inserted, imported, or repaired, and `updated_at` moves on changes no user made. Before reusing an existing timestamp for an API field, confirm exactly which user actions move it.

```ruby
# BAD
t.index %i[user_id created_at]
scope :up_to, ->(message) { where("id <= ?", message.id) }

# GOOD
t.datetime :attached_at, null: false
t.index %i[user_id attached_at]
scope :up_to, ->(message) { where(sent_at: ..message.sent_at) }
```

Do not express "everything up to this record" as an id range. Ids can be inserted with arbitrary values later.

Preference: never sort application data by `created_at`. Use a column with application meaning or an explicit position column.

Use `string`, not `text`, for short bounded values such as enum-like labels. For a level or category column, prefer an enumerated string over a bare integer; the integer carries no meaning on its own. When unsure about a type, follow the Rails Guides.

Represent the same domain value with the same type and format the existing tables use (a graduation year stored as the same string form everywhere), or state the reason for deviating. Mismatched representations make joins awkward.

Prefer `datetime` over `time`. Use `time` only when the value has no date component at all, and say so.

A column stores domain meaning, never presentation. A "yellow flag" boolean or a display name next to a code invites the two to drift. If the meaning cannot be stated in one sentence, the column needs a better definition.

Persist a computed attribute only with a stated reason.

When an enum models a domain concept, check that its values cover every real case and that it mixes no orthogonal dimensions. Two values that could both be true at once belong in two columns.

Add a CHECK constraint for an integer whose valid range is known, instead of relying on model validation alone. Do not add a constraint that guards a state the application cannot produce; ask for the concrete failure case first.

```ruby
# GOOD
add_check_constraint :answers, "scale_value BETWEEN 1 AND 5",
  name: "answers_scale_value_range"
```

Do not enumerate application-level enum values in a column comment. The list grows in code and the comment drifts.

Keep human-readable labels for code values in the locale files, not in a `name` column of a lookup table.

```ruby
# BAD
t.string :code, null: false
t.string :name, null: false, comment: "Display name of the summary kind"

# GOOD
t.string :code, null: false   # label via I18n.t("summary_kinds.#{code}")
```

Preference: use a JSON column for a free-form field that is likely to grow into a nested structure. When the stored structure can change shape, plan a version field so old rows stay readable.

## 4. Cardinality and shape

Confirm the intended cardinality with the business before approving a new table: can one user have many attempts of the same lesson? The answer decides whether a unique index is needed and whether the model is right.

Make unique indexes express the real cardinality. If the domain is one-to-one, constrain the single column and consider `has_one`; a composite unique key permits rows the business rule forbids. Ask for the strictest constraint the domain allows.

Check `has_one` against reality. When the parent can be linked to many contexts (one video in many contracts and many periods), the child is `has_many`, and a `has_one :through` cannot be built at all in that case. A wrong `has_one` silently blocks legitimate rows.

Confirm that a new table or data mart covers every variant of the concept its name claims. Widen the content or narrow the name.

Keep a table's columns within the concept its name denotes. A `schedules` table holds period data, not notification settings; a column outside the concept means a misplaced attribute or a misnamed table.

Before adding a table named after one external vendor, model the concept generically (a meeting room, not a vendor's meeting room) and check how similar concepts are already named.

Keep naming and modelling decisions consistent with the sibling tables in the same domain. When a new table diverges in foreign key naming or in how options are stored, align it.

State the normalisation decision in the schema PR: which columns move to their own tables and which deliberately stay.

Preference: use delegated types when a table needs nullable columns that depend on a mode and the model branches with `case` on that mode. Those two signals mark the pattern. A callback that clears the columns unused by the current type is a data-integrity risk; prefer the structural split or `NOT NULL`.

Preference: model a review outcome or human approval step as its own record (one table per outcome under a shared review record), not a decision string plus outcome-specific nullable columns on the request. The decision has its own actor and time.

Preference: keep a history of status changes per entity instead of overwriting one current-status row when the history has business value and volume is small.

## 5. Indexes and constraints

Every index names the query it serves. Question a single-column index whose use is not obvious; an index without a known query costs writes and storage for nothing.

Decide the index strategy when creating the table, or state in the PR that indexes come later. Log tables are the ones that get forgotten. Verify query behaviour against production-like volume before release, even when the table is expected to stay small.

Justify `lock_version` with the concurrent-update scenario it prevents. Drop it when the rows are effectively never updated.

When the team uses a database feature for the first time (a CHECK constraint, a generated column), align on when it should be used before the pattern spreads.

## 6. Naming

Name tables in the plural, after what one row is. A table of verification requests is `..._requests`, not `..._verifications`. Keep pluralisation consistent across a family; if one name had to be singularised to fit a length limit, align the family in a follow-up.

Foreign key columns end in `_id`. Name actors by their role noun.

```ruby
# BAD
t.bigint :created_by
t.bigint :updated_by

# GOOD
t.references :creator, foreign_key: { to_table: :users }
t.references :updater, foreign_key: { to_table: :users }
```

Name a table or column after the entity the schema already has (`video_bundle_id` for `video_bundles`), not after a UI or business synonym.

A boolean reads as an unambiguous predicate, and follows the prefix convention the schema already uses. If the existing columns carry `is_`, keep `is_`; either way `is_promotion_contract_notification` fails, because it is not a predicate and does not say what triggers it. Name the boolean after the decision it records (`display_hiring_universities`), not after a fact it does not assert (`hiring_universities_available`). The comment says exactly when it is true.

Include the unit in duration and size columns, with seconds as the base unit for durations: `approximate_time_seconds`, not `approximate_time_minutes`.

Do not encode a presentation position (axis, side, order) or an incidental property (`action_sequence_id`) in a column name. Name the quantity: `target_conversion_rate`, `action_id`.

Name aggregates by their window. A one-week sum is `weekly_...`, never `..._totals`.

Name join tables after the relationship (`memberships`, `enrollments`), not by concatenating the two model names. Give a polymorphic association a concrete domain name rather than a generic `-able` placeholder such as `settable`.

Tables in one feature family share a prefix; a qualifier that means "belongs to X" reads as a prefix, and the PR lists the trade-offs of the chosen name. Accept a generic table name only when the existing schema already follows that pattern.

Use common words. A rare word such as `quarantined_at` needs a reason or a plainer replacement.

A SQL alias describes the rows it holds. Aliasing a filtered subset as the base table name (`filtered_scout_users AS users`) makes every later edit assume the full table.

## 7. Comments

Give every new table a comment that says what one row is. Omit "table", "table for storing", and "manages"; a table does not manage anything, and a comment such as "file deletion task management" does not say that each row is one request.

```ruby
# BAD
create_table :report_deletion_requests, comment: "Table for managing report deletion tasks" do |t|

# GOOD
create_table :report_deletion_requests, comment: "A request to delete one report file" do |t|
```

Add a comment to every column a migration creates. The comment states whose value it is and, for a boolean, what true means. "Handled" or "flag" leaves the actor and the meaning open; ask until the comment names them.

Do not repeat in a comment what a foreign key already states ("corresponds to companies.id"). The comment carries only what the schema cannot.

Do not put project or initiative names in table or column comments. They are transient context, not a property of the data.

When a migration defines a view or raw SQL, comment each non-obvious condition (what "valid" means, why one row per company). One top-level comment does not explain the conditions, and inlining a CTE removes the name that used to. When logic moves from application code into a view, move its explanatory comments with it.

## 8. Migrations

Add a `NOT NULL` column to a populated table in three steps: add it nullable, backfill, then `change_column_null`. Do not invent a default only to satisfy the constraint; a default that is not semantically needed hides missing data. Post the query showing zero NULLs in the PR before the constraint migration.

```ruby
# BAD
add_column :messages, :status, :string, null: false, default: "completed"

# GOOD (three migrations, in order)
add_column :messages, :status, :string, comment: "Delivery state of the message"
Message.in_batches.update_all(status: "completed")   # data task; skips validations because none reads the new column yet
change_column_null :messages, :status, false
```

Keep schema changes and application changes in separate PRs. Rename through `alias_attribute` first, switch the callers, and rename the column in a later PR; destructive changes go last so rollback stays possible. When a model is shared across applications, the alias lives in the shared model so consumers carry no TODO about the old name.

```ruby
# PR 1: model
alias_attribute :publication_type, :event_category
# PR 2: callers use publication_type
# PR 3: migration
rename_column :contracts, :event_category, :publication_type
```

`down` restores the previous definition. Dropping a replaced view or function on rollback leaves the application referencing a missing relation; the old definition goes back in `down`.

A PR that adds a migration includes the resulting `db/schema.rb` diff. Without it the migration has not been run.

When a migration replaces a whole SQL definition, the PR states which clauses changed. The diff shows only the full text.

When the version number collides with migrations merged in the meantime, renumber it and say so; the content is unchanged.

Before dropping a table, confirm whether it holds re-computable replica data or real data. Back up real data first.

Verify structural changes (schema regeneration, table rebuilds, column additions on large tables) on a staging deployment with production-like data before merging, and include a risk note for large tables.

Plan the release timing of migrations that rebuild materialized views or touch other heavy objects, and estimate how long each refresh takes.

In a data task, process independent rows one by one. Locks and wide transactions around rows that do not affect each other add complexity without protecting anything.

When a new optional association is added to an existing table, note in the PR that historical rows are to be backfilled, even when the backfill is deferred.

## Checklist

- [ ] Does every reference column use `t.references ... foreign_key: true`, or carry a comment saying why a foreign key is impossible?
- [ ] Is every boolean `NOT NULL` with a default, and does every `null: true` column have a stated reason?
- [ ] Does any column store a value derivable from other rows or from the stored file, without a measured need?
- [ ] Does the diff give `created_at` or `updated_at` business meaning where an event timestamp belongs?
- [ ] Does each enum cover every real case without mixing two dimensions, and is a two-state value a boolean?
- [ ] Do the unique indexes and `has_one`/`has_many` declarations match the cardinality the business confirmed?
- [ ] Does every index name the query it serves, and was the index strategy decided for the new table?
- [ ] Is every table plural and named for what one row is, every foreign key suffixed `_id`, every actor a role noun?
- [ ] Does every boolean name read as an unambiguous predicate in the schema's existing prefix style?
- [ ] Do duration and size columns carry their unit, and aggregates their window?
- [ ] Does every new table and column have a comment saying what one row or value is, without "table", "manages", or a project name?
- [ ] Is a `NOT NULL` addition split into add, backfill, and `change_column_null`, with evidence of zero NULLs in the PR?
- [ ] Does `down` restore the previous definition, and is `db/schema.rb` in the diff?
- [ ] Are schema changes and application changes in separate PRs, with `alias_attribute` ahead of any rename?
- [ ] Are the same type, format, prefix, and naming used as the sibling tables in this domain?
